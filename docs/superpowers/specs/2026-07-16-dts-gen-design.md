# 设计文档:硬件描述 → 分层 Devicetree 生成工具

日期:2026-07-16

## 一、背景与目标

内核开发中,devicetree 通常按硬件层次(SoC / 核心板 / 底板)分层维护,以`.dtsi`/`.dts` 的 `#include` 关系体现,从而在多个核心板/底板之间复用 SoC 层、核心板层的描述。手工编写这类分层 devicetree,尤其是补充外围芯片(USB repeater、PCIe PHY 等)的节点,存在大量重复性工作。

本工具的目标:基于结构化的硬件连接数据和芯片信息源,自动生成/校验分层 devicetree,减少手工重复劳动,同时保证生成结果的语法和绑定合规性。

## 二、输入源

1. **硬件连接数据**:自定义简化格式(yaml/csv),描述器件间的连接关系(引脚、总线挂载、phandle 引用关系)。不支持解析 EDA 工具原生 netlist 格式(如 Altium/OrCAD 导出格式)。
2. **芯片信息源**:IP catalog 提供的结构化数据源(非 PDF)。前期设想的"自动解析 PDF datasheet"因实际数据源不是 PDF 格式而不适用,工具应直接对接 IP catalog 的结构化数据接口/导出格式。

## 三、核心设计:分层架构

### 3.1 层次结构

```
SoC 层    (soc.dtsi)     — SoC 内部外设、地址映射、公共控制器
   ↓ #include
核心板层  (som.dtsi)     — 引用 soc.dtsi,补充核心板专属内容
   ↓ #include
底板层    (board.dts)    — 引用 som.dtsi,补充底板专属内容
```

每一层是独立、可复用的 devicetree 文件。SoC 层通常直接复用内核树中已有的官方文件,工具主要处理核心板层和底板层的生成。

### 3.2 模块(Module)

**定义:模块 = 根据 phandle 引用关系自动聚类出来的节点群,不是预定义模板。**

聚类方法:对硬件连接数据构建 phandle 引用关系图,做连通分量分析(connected components),每个连通分量即为一个模块(如 USB 模块 = dwc3 + eUSB2 PHY + repeater 节点的连通集合)。

这一设计避免为每种可能的子系统组合预先维护模板,天然适配任意拓扑组合。

### 3.3 框架(Skeleton)

**定义:某一层的总线结构、节点骨架,由该层包含的模块列表自动推导。**

推导方法:
1. 收集该层所有模块涉及的节点,提取各自需要挂载的总线类型
2. 按总线类型分组,生成对应的总线容器节点
3. 若所需总线容器已在上层(如 SoC 层)存在,识别为复用,不重复生成,仅将模块节点挂载为其子节点

## 四、完整处理流程

```
第一阶段:输入解析
  硬件连接数据(yaml/csv) + IP catalog结构化数据
    → 统一的硬件描述中间表示(节点候选 + phandle引用关系图)

第二阶段:模块识别(先于节点生成)
  对phandle关系图做连通分量分析 → 得到模块列表

第三阶段:框架推导
  根据模块列表反推总线骨架
    → 识别可复用的已有上层总线节点
    → 确定需要新建的总线容器节点

第四阶段:逐层生成节点
  规则引擎(可扩展规则文件驱动)将硬件特征映射为具体dt属性/语法
    → 按框架逐个填充模块对应的节点

第五阶段:自下而上校验(与生成方向相反)
  ① 节点语法校验(单节点 dtc 语法)
  → ② 模块校验(模块内 phandle 引用自洽性)
  → ③ 框架校验(该层总线/地址范围无冲突)
  → ④ 层级校验(各层通过 #include 叠加后,整棵树 dtc 编译 + dtbs_check 通过)
```

处理时序明确:模块识别在节点生成**之前**完成,先分析输入拿到模块列表,再推导框架、生成节点——不是先生成全部节点再事后识别模块。

## 五、规则引擎

### 5.1 职责

将硬件特征(如"存在 reset-gpios 属性"、"需要 vdd-supply")映射为具体的 devicetree 语法/属性写法。

### 5.2 规则来源与维护(独立的离线子流程)

```
扫描内核树中已有的 .dts/.dtsi 文件
  → 自动提取"硬件特征模式 → devicetree写法"的候选映射
  → 人工筛查/确认候选规则
  → 写入可扩展的规则文件
```

此学习子流程与主生成流程解耦:产出物是规则文件本身,主流程运行时只读取已确认的规则文件,不在生成过程中实时扫描内核树。

规则文件本身应为可配置/可扩展格式(如 yaml),支持用户后续手动补充新芯片/新场景的映射规则。

## 六、输出与验证

- **当前范围**:生成单个层级下的模块/节点,合并为完整分层设备树的能力属于本设计范围内的既定目标(而非预留扩展),完整流程需支持从模块生成到层级校验的全链路。
- **验证方式**:生成结果自动调用 `dtc`(devicetree compiler)和 `dtbs_check` 进行语法与绑定合规性校验,校验遵循上述"自下而上"的四级顺序,不合规时明确报错并指出层级。

## 七、技术选型

- **实现语言**:Python
- **使用形式**:先实现命令行工具(CLI),交互式界面(网页/TUI)作为后续可选扩展层,不在当前实现范围内
- **PDF 自动解析**:因实际芯片信息源为 IP catalog 结构化数据而非 PDF,此前设想的 PDF 解析能力(传统提取优先、LLM 兜底)暂不需要实现;若未来出现需要处理 PDF datasheet 的场景,可作为独立输入适配器补充,不影响当前架构

## 八、待细化事项(留待实现计划阶段展开)

- IP catalog 结构化数据源的具体接口/格式尚未明确,需要进一步调研对接方式
- 模块的语义标签(如识别出的连通分量具体是"USB 模块"还是别的)如何从节点信息反推,具体算法待细化
- 规则引擎的规则文件具体 schema 设计
- 内核树规则学习子流程的具体实现方式(静态分析 dtc 编译后的语义,还是基于文本模式匹配)
